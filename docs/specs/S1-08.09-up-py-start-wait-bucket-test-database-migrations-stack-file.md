## User story

Requirement served: none names local stack tooling (gap, see the spec). It enables the local-run rule in CLAUDE.md.

```gherkin
Feature: up.py: start, wait, bucket, test database, migrations, stack file
  As a considered dresser
  I want the whole app to run locally in its own worktree
  So that I and the agents can test it end to end without clashes
```

`python scripts/dev/up.py up|down|status|go|e2e [--budget N]` is the only code that calls docker: allocate project and ports, build images (cache hit is a no-op), run compose, start the api and web services from S1-07.10, wait for health in parallel, create the S3 bucket, apply migrations to a template database and create `slaydrip_test` from it on every run, render the realm, write stack.json with every config-contract key and the test database URL, print per-step timings (build time reported separately) and exit non-zero over budget. `go` and `e2e` run the S1-07.06 Go tool service and the S1-07.07 Playwright service on the stack network, with this ticket only adding the per-worktree project name and ports; those containers get no Docker socket. Governing design: [S1-08](S1-08-local-stack.md), [ADR-0016](../adr/0016-per-worktree-local-stack.md).

## Acceptance criteria

```gherkin
Scenario: Cold start of the local stack takes at most 30 seconds
  Given a worktree with no running stack and the stack's images already pulled
  When I run "python scripts/dev/up.py up --budget 10"
  Then the command exits with code 0 within 30 seconds
  And the API, the S3 bucket, the test database and Keycloak all answer their checks

Scenario: No .env file is read
  Given a new worktree with no .env file
  When I run "python scripts/dev/up.py up"
  Then the stack starts and no .env file is read or created
  And every local value comes from compose.yaml or a committed file under infra/dev/

Scenario: The test database is fresh and migrated on every run
  Given a row was written to the test database in an earlier run
  When I run "python scripts/dev/up.py up"
  Then the test database "slaydrip_test" exists with every migration applied
  And the earlier row is gone and the dev database is untouched
```
