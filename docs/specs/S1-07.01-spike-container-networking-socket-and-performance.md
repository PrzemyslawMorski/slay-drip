## User story

Requirement served: none names containerised tooling. It enables F7 (through S1-06) and the local-run rule in CLAUDE.md. See the spec's Problem section.

```gherkin
Feature: Containerised tooling design questions are answered before images are built
  As a considered dresser
  I want the container design checked on Windows, macOS and Linux hosts
  So that the tool tickets do not pick an untested networking or file-watch approach
```

The Playwright tests and the smoke scripts reach the stand-ins at `127.0.0.1` (the Keycloak issuer must match `KC_HOSTNAME`, ADR-0010), which is the container itself from inside a tool container. The stack-lifecycle Playwright scenarios run `docker compose` from the test process. File watching and test speed on Docker Desktop bind mounts are unmeasured. This Spike writes one discovery note that answers these, with a recommendation. It does not build anything. Spec: [S1-07](S1-07-containerised-dev-tooling.md).

## Acceptance criteria

```gherkin
Scenario: The same commands work on Windows, macOS and Linux hosts
  Given the documented tool commands
  When they are read for each host
  Then every command starts with "docker compose" and uses no shell syntax that differs by host
  And no command needs a Makefile, a shell script or a PowerShell script
```

## Notes

**Agent brief**

- **Role:** `architect` (see `.claude/skills/tickets-from-spec/references/roles.md`)
- **Goal:** One discovery note that recommends how tool containers reach the stand-ins, how Playwright stack tests run Compose, and how file watching and speed are handled on Windows and macOS hosts.
- **Read first:** [S1-07 Design](S1-07-containerised-dev-tooling.md#design), [ADR-0014](../adr/0014-containerised-dev-tooling.md), [ADR-0010](../adr/0010-identity-provider-keycloak.md), `docs/discovery/_template.md`, `frontend/tests/support/keycloak-stack.ts`
- **Files to change:**
  - `docs/discovery/2026-11-02-containerised-tooling-networking-and-performance.md`, from `_template.md`: options, evidence, recommendation, the questions it leaves for the owner
- **Do not touch:** Compose, Dockerfiles, scripts, ADRs. Do not accept or change ADR-0014.
- **Covers scenarios:** `The same commands work on Windows, macOS and Linux hosts`
- **Done when:** the note follows its template, answers the four questions below with evidence from a run on at least one Windows host and one Linux or macOS host (or says which host was not available), and leaves its status as a proposal for the owner. The 2-day time box is respected.
- **Out of scope:** Building any image or service (S1-07.06 onward).
- **Open questions:** The note must answer: (1) how a tool container reaches Keycloak, PostgreSQL and S3 while the issuer stays `http://127.0.0.1:8180/realms/slay-drip` (host networking, an extra hosts entry, a shared network namespace, or a reverse proxy); (2) the owner decided that stack setup stays on the host with no stack setup in any tool container, so: what is the one documented host command that starts or stops the stack, and how the containerised Playwright run reaches the running stack (the stack-lifecycle project is excluded from the container run; list options for keeping those scenarios, do not choose); (3) where the repo and `node_modules` live on Windows and macOS hosts (bind mount, named volume, WSL 2) and whether polling is needed for Vite; (4) a measured time for `go test ./...` and `npm run test:unit` through bind mounts. The owner decides the performance target, not this ticket.
