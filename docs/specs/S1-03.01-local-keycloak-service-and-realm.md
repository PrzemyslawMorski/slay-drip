## User story

Requirement served: the Session 1 walking skeleton row and F1.1 (18+ gate at sign-up), through the local identity provider that sign-up will use.

```gherkin
Feature: Local identity provider for development
  As a considered dresser
  I want sign-up and sign-in to run on my machine against the same identity provider as production
  So that the Session 1 sign-up work can be built and tested offline
```

Add the local Keycloak service and its realm import. The design and the reasons are in [ADR-0010](../adr/0010-identity-provider-keycloak.md) and [S1-03](S1-03-local-keycloak.md), sections Design and Acceptance criteria. Do not restate them here. Local values are throwaway and synthetic only.

## Acceptance criteria

```gherkin
Scenario: The local identity provider starts beside PostgreSQL and the S3 stand-in
  Given the local stack is stopped
  When I run "docker compose up -d" from the repo root
  Then the keycloak service is running and reports healthy
  And keycloak listens on 127.0.0.1 only
  And the database and object-storage services are still running
  And keycloak has no named volume

Scenario: The local identity provider publishes its discovery document and keys
  Given the keycloak service is healthy
  When I request the discovery document and the JWKS URL from the config contract
  Then both respond with HTTP 200
  And the discovery issuer equals the value of OIDC_ISSUER_URL
  And the discovery document gives the JWKS URL equal to OIDC_JWKS_URL
  And the discovery document lists S256 as a supported code challenge method

Scenario: The PWA client refuses sign-in without a PKCE S256 challenge
  Given the slay-drip realm is imported
  When an authorization request for client slay-drip-pwa arrives without a code challenge
  Then the request is refused and no login form is shown
  And the redirect URIs of slay-drip-pwa list only paths on http://localhost:5173
```

## Notes

**Agent brief**

- **Role:** `infra-engineer` (see `.claude/skills/tickets-from-spec/references/roles.md`)
- **Goal:** `docker compose up -d` starts a pinned Keycloak that imports the `slay-drip` realm from `infra/dev/` and serves discovery, JWKS and the public PWA client with PKCE S256.
- **Read first:** [S1-03 Design](S1-03-local-keycloak.md#design), [ADR-0010](../adr/0010-identity-provider-keycloak.md), [ADR-0005](../adr/0005-local-cloud-emulation.md), [local development guide](../local-development.md) (config contract and the feature checklist), [security guide](../security.md) sections 5, 9 and 13.
- **Files to change:**
  - `compose.yaml`: add the `keycloak` service. Pinned exact tag; `127.0.0.1:8180:8080`; `env_file` for the admin config; the realm directory mounted read-only at `/opt/keycloak/data/import`; dev mode with `--import-realm`; `KC_HOSTNAME=http://127.0.0.1:8180`; healthcheck; `restart: unless-stopped`; no named volume.
  - `infra/dev/keycloak/realm/slay-drip-realm.json`: realm `slay-drip` with `registrationAllowed: false` and `accessTokenLifespan: 300`. Client `slay-drip-pwa` (public, standard flow, PKCE `S256` attribute, direct grants and implicit off, redirect URI `http://localhost:5173/auth/callback`, web origin `http://localhost:5173`, audience mapper adding `slay-drip-api`). Client `slay-drip-backend-admin` (confidential, client credentials, service account with realm-management `manage-users` only; throwaway secret). Three synthetic users on `example.test`, invented names, one credential each, no attributes.
  - `infra/dev/keycloak/local-admin.conf`: `KEY=VALUE` lines for the bootstrap admin username and password. The name must not end in `.env`.
- **Do not touch:** `scripts/dev/` (S1-03.02), `docs/local-development.md` (S1-03.03), any app code, and any `.env` file. Never read, search, print or create `.env` files.
- **Covers scenarios:** `The local identity provider starts beside PostgreSQL and the S3 stand-in`; `The local identity provider publishes its discovery document and keys`; `The PWA client refuses sign-in without a PKCE S256 challenge`
- **Done when:** the three scenarios pass. Checks: `docker compose config --quiet` in the repo root; `docker compose up -d keycloak` then `docker compose ps`; `curl -sS -f http://127.0.0.1:8180/realms/slay-drip/.well-known/openid-configuration`; the JWKS URL returns `keys`; the PKCE refusal request is sent with curl and its response recorded in the PR. Do not start the other services' changes or change `database` or `object-storage`.
- **Out of scope:** the smoke script and the sign-in flow (S1-03.02); the docs (S1-03.03); sign-up, the 18+ gate and consent (later Session 1 tickets); Scaleway deployment and the production database (ADR-0010 spike).
- **Open questions:** None blocking. Verify these in the PR and record the answers:
  - **Image tag.** The 26.8.x suggestion is unverified. Pick an exact stable tag that exists on Docker Hub (`keycloak/keycloak`) and check it against the upstream release (quay.io/keycloak/keycloak). If Docker Hub lacks it, use the upstream registry and say so. Record the tag, the page URL, the date checked, and the digest if shown. Do not use `latest`.
  - **Bootstrap variable names** for the pinned tag (`KC_BOOTSTRAP_ADMIN_USERNAME` and `KC_BOOTSTRAP_ADMIN_PASSWORD`, or the older `KEYCLOAK_ADMIN*`).
  - **Healthcheck probe.** Use a tool the pinned image ships (for example the built-in health endpoint on the management port inside the container, with `KC_HEALTH_ENABLED=true`). Do not install packages or change the base image.
  - **Host port.** `8180` is the proposed free port. If it is taken on your machine, pick another, use it in the realm and config values, and say so in the PR.
  - **Realm import.** Confirm the realm imports on first start, and confirm that users, both clients and the service-account role exist afterwards.
  - **Service-account role.** Confirm that `manage-users` is enough for user create, logout and delete. Do not add `view-realm` or `manage-clients` unless a check fails and the PR records why.
  - **Callback path.** `/auth/callback` is proposed. The frontend ticket that adds sign-in confirms it.
- **Constraints:** EU-only (local only, no cloud). No AWS resource, SDK or CLI. Do not reference any other identity vendor. Secrets are throwaway values, valid only for this stack, and they never go in the repo outside `infra/dev/`. Synthetic personas only: no real names, emails, ages, dates of birth or addresses. Do not decide any ADR-0010 open item (passkeys or magic links, Scaleway region, backup erasure window, who runs the service). Those are not needed here.

Hard-rule tests this ticket must pass after its change, which are not in its Covers line: S1-03.09 (EU regions), S1-03.10 (no AWS reference) and S1-03.11 (synthetic personas only). They are guards, and they are listed here so the executor runs them.
