## User story

Requirement served: Privacy, GDPR & trust, rules 2, 4 and 8 (EU-only, granular consent, 18+ at sign-up). The review confirms that the local identity provider holds only synthetic data and that its throwaway secrets stay local.

```gherkin
Feature: Privacy review of the local identity provider
  As a considered dresser
  I want the local identity provider reviewed for personal data and secrets before it is relied on
  So that no real person's data or production secret can enter the repo through the local stack
```

Read-only review. It writes its findings in the ticket Notes or a PR comment, and it does not edit files. Scope and checks are in [S1-03](S1-03-local-keycloak.md#quality-and-compliance) and [security guide](../security.md) sections 1, 3, 9 and the PR checklist.

## Acceptance criteria

```gherkin
Scenario: The local realm holds only synthetic personas
  Given the committed realm file is infra/dev/keycloak/realm/slay-drip-realm.json
  When I review its users, attributes and client settings
  Then every user email ends in example.test and every name is invented
  And no user has an age, date of birth, postal address, body, measurement or special-category attribute
  And the public client slay-drip-pwa holds no secret
```

## Notes

**Agent brief**

- **Role:** `privacy-reviewer` (see `.claude/skills/tickets-from-spec/references/roles.md`)
- **Goal:** a written finding for each blocking rule that applies to the local identity provider: synthetic data only, no personal data or age or body data in Keycloak, self-registration on (local only, ADR-0010 amendment), throwaway secrets kept local, no real host or secret in docs, and no AWS or non-EU vendor in the files.
- **Read first:** [S1-03](S1-03-local-keycloak.md), [security guide](../security.md) (sections 1, 2, 3, 9, 10 and the PR checklist), [ADR-0010](../adr/0010-identity-provider-keycloak.md) (Compliance check), `docs/code-review/README.md`, `docs/code-review/secrets-and-logging.md`, `docs/code-review/eu-only-processing.md`, `docs/code-review/age-gate.md`.
- **Files to change:** None (read-only)
- **Do not touch:** any file. Do not accept an ADR-0010 open item on the team's behalf; report it as "needs a decision" if it comes up. Never read, search, print or create `.env` files.
- **Covers scenarios:** `The local realm holds only synthetic personas`
- **Done when:** each blocking rule that applies has a finding or a "passes, because" line. The review confirms: no real name, email, age, date of birth, address or body data in the realm; no secret outside `infra/dev/`; no production value in any file; `compose.yaml` and the scripts use only EU-region or local values; no AWS resource, SDK or CLI; the admin client holds only what the smoke needs.
- **Out of scope:** fixing findings (the owning ticket does that); the 18+ gate itself, which the sign-up ticket tests; the ADR-0010 open items.
- **Open questions:** None.
- **Constraints:** Synthetic personas only. Note any throwaway password or secret that could be mistaken for a real one, and confirm it is labelled throwaway. Confirm that `registrationAllowed` is `true` and that the server-side 18+ gate is still open and that no age field exists anywhere. Note that a live check of the realm settings needs `view-realm`, which the admin client does not hold, so the registration check is static.

Findings go in the ticket Notes or a PR comment. Use the rule IDs from `docs/code-review/` where they exist.
