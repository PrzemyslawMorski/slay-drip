## User story

```gherkin
Feature: Photos are queued for deletion in the same transaction as their rows
  As a considered dresser
  I want my wardrobe photos queued for deletion when I withdraw consent or delete my account
  So that no photo stays behind if storage fails once
```

Context: ADR-0013, erasure paths 1 and 3. Object storage cannot join the database transaction. This ticket records each photo key inside the transaction that deletes its item. S1-06.24 deletes the objects from that queue.

## Acceptance criteria

```gherkin
Scenario: Photo keys are recorded in the same transaction that deletes the items
  Given a signed-in person with two stored wardrobe photos
  When the person withdraws wardrobe-photo consent
  Then both photo keys are recorded for deletion
  And the recording and the item deletion commit together, or neither does

Scenario: Account deletion records every photo key
  Given a person with stored wardrobe photos and saved outfits
  When the person deletes their account
  Then every photo key is recorded for deletion in the same transaction that deletes the rows
```
