## User story

Requirement served: the Session 1 walking skeleton row and F1.1 (18+ gate at sign-up). The smoke script proves that the local provider signs in a persona the way the PWA will, and that the backend admin client can delete a user and revoke sessions, which F6.1 needs.

```gherkin
Feature: Local identity provider smoke check
  As a considered dresser
  I want one command to prove that sign-in and account deletion work on my machine
  So that the Session 1 sign-up and deletion work starts from a known-good provider
```

The script follows the style of `scripts/dev/s3_smoke.py`. The design is in [S1-03](S1-03-local-keycloak.md#design). Do not restate it here.

## Acceptance criteria

```gherkin
Scenario: A synthetic persona signs in with authorization code and PKCE S256
  Given the slay-drip realm is imported with the synthetic persona smoke.user@example.test
  When the smoke script runs the authorization code flow with PKCE S256 for client slay-drip-pwa
  Then the token endpoint returns an access token and an ID token
  And the access token audience includes slay-drip-api
  And the script ends with "OK: Keycloak smoke passed"

Scenario: The backend admin client can create, log out and delete a throwaway user
  Given client slay-drip-backend-admin is configured for client credentials
  When the smoke script gets a token, creates a throwaway synthetic user, revokes its sessions and deletes it
  Then the create, logout and delete calls return HTTP 201, 204 and 204
  And the throwaway user is no longer found afterwards

Scenario: Self-service registration is on in the local realm
  Given the committed realm file is infra/dev/keycloak/realm/slay-drip-realm.json
  When the smoke script reads that file
  Then registrationAllowed is true
  And the script reports this as a static check of the committed file
```

## Notes

**Agent brief**

- **Role:** `infra-engineer` (see `.claude/skills/tickets-from-spec/references/roles.md`)
- **Goal:** `python scripts/dev/keycloak_smoke.py` checks the running local provider end to end and ends with `OK: Keycloak smoke passed`.
- **Read first:** [S1-03 Design](S1-03-local-keycloak.md#design), [local development guide](../local-development.md), `scripts/dev/s3_smoke.py` (style reference), [ADR-0010](../adr/0010-identity-provider-keycloak.md), [security guide](../security.md) sections 5 and 9.
- **Files to change:**
  - `scripts/dev/keycloak_smoke.py`: `set -euo pipefail`; defaults for `OIDC_ISSUER_URL`, `OIDC_CLIENT_ID`, `OIDC_AUDIENCE`, `OIDC_REDIRECT_URI`, `KEYCLOAK_BASE_URL`, `KEYCLOAK_REALM`, `KEYCLOAK_ADMIN_CLIENT_ID`, `KEYCLOAK_ADMIN_CLIENT_SECRET` and the smoke persona's username and password, matching the local values in S1-03.01; four steps, printed as `1/4` to `4/4`, each with a clear failure message. Steps: (1) discovery document and issuer; (2) JWKS URL matches discovery and returns keys; (3) PKCE sign-in as the persona, with the audience check; (4) admin client lifecycle on a throwaway user, plus the static registration check. Create the throwaway user with a unique name and delete it at the end, using a trap. Never print a token or a secret.
- **Do not touch:** the realm file and `compose.yaml` (S1-03.01). If the script needs a realm change, stop and report it in the PR rather than editing it. Docs (S1-03.03). Never read, search, print or create `.env` files.
- **Covers scenarios:** `A synthetic persona signs in with authorization code and PKCE S256`; `The backend admin client can create, log out and delete a throwaway user`; `Self-service registration is on in the local realm`
- **Done when:** the three scenarios pass. Check: with the stack running (S1-03.01), `python scripts/dev/keycloak_smoke.py` ends with `OK: Keycloak smoke passed`. Run it twice to confirm the throwaway user is cleaned up each time. Run it once with a wrong persona password and confirm it fails at step 3 with a message that does not print the password.
- **Out of scope:** the realm and compose service (S1-03.01); docs (S1-03.03); sign-up, the 18+ gate and account deletion in the app (later tickets).
- **Open questions:** None.
- **Implementation constraints:**
  - Use only `curl`, `openssl`, `base64`, `sed`, `grep` and `date`, which ship with Git Bash. No `jq`, no AWS CLI, no SDK.
  - PKCE: verifier from `openssl rand`, 64 characters from the base64url alphabet. Challenge is `BASE64URL(SHA256(verifier))`, with no padding.
  - Authorization request: `GET` with `response_type=code`, `scope=openid`, `client_id`, `redirect_uri`, `state`, `nonce`, `code_challenge` and `code_challenge_method=S256`. Use a cookie jar. Do not follow redirects. Read the form `action` from the login page HTML and decode `&amp;`.
  - Token request: `POST` form with `grant_type=authorization_code`, `code`, `redirect_uri`, `client_id` and `code_verifier`.
  - Audience: decode the access token payload with `base64 -d` after converting base64url and restoring padding. Check that `slay-drip-api` appears in `aud`.
  - Registration check: a file check only. The admin client does not hold `view-realm`, so do not add it. Label the line as static in the output.
  - The HTML parse depends on the pinned Keycloak markup. Note this in a comment at the top of the script.
  - Synthetic data only. The throwaway user is `smoke-<unix-time>-<pid>@example.test` with no attributes.
- **Constraints:** EU-only (local only). No AWS resource, SDK or CLI. Secrets are throwaway values valid only for this stack, and they stay in `infra/dev/`. Do not decide any ADR-0010 open item.

Local defaults match S1-03.01: issuer `http://127.0.0.1:8180/realms/slay-drip`, client `slay-drip-pwa`, redirect `http://localhost:5173/auth/callback`, audience `slay-drip-api`, admin client `slay-drip-backend-admin`, persona `smoke.user@example.test`.
