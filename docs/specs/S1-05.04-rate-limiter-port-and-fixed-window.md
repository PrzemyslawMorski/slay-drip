## User story

Requirement served: security guide §10 and BE-47 (blocking). Design: a limiter behind a port, with an in-memory fixed window per subject key.

```gherkin
Feature: Rate limiting on account and wardrobe routes
  As a considered dresser
  I want the service to refuse bursts of requests from one account
  So that one account or a script cannot exhaust the service or its storage
```

The limiter counts requests per subject key. The subject key is the verified `sub`, so one account's count does not affect another's. The window and the limit come from config keys, and the clock is injected so tests need no sleeps (BE-28).

## Acceptance criteria

These are unit-level scenarios. The spec scenarios they support are turned green through HTTP by S1-05.05 and S1-05.06.

```gherkin
Scenario: The limiter counts each subject key separately
  Given a limiter with a limit of 2 per window
  And subject "sub-a" has made 2 requests in the window
  When subject "sub-b" makes a request in the same window
  Then the limiter allows the request for "sub-b"
  And the limiter refuses the next request for "sub-a"

Scenario: The limiter opens a new window when the window has passed
  Given a limiter with a limit of 1 per window
  And subject "sub-a" has used the limit in the current window
  When the injected clock moves past the end of the window
  Then the limiter allows the next request for "sub-a"
```
