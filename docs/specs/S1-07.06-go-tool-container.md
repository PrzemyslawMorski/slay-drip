## User story

Requirement served: none names containerised tooling. It enables F7 (through S1-06) and the local-run rule in CLAUDE.md. See the spec's Problem section.

```gherkin
Feature: Go tooling in a container
  As a considered dresser
  I want the backend tests, lint and vulnerability checks to run in a Go container
  So that no Go install is needed on my machine
```

Adds the `go` tool service (compose profile `tools`, so `docker compose up` does not start it) and its pinned image. Go version follows `backend/go.mod` (ADR-0007). A named volume holds the module and build cache. The tool versions stay pinned through `tool` directives in `go.mod`. Governing design: [S1-07](S1-07-containerised-dev-tooling.md), [ADR-0014](../adr/0014-containerised-dev-tooling.md). Spec: [S1-07](S1-07-containerised-dev-tooling.md).

## Acceptance criteria

```gherkin
Scenario: Each toolchain runs in a container with no host install beyond Docker
  Given a host with only Docker and Compose v2 installed
  When a developer runs a Go, Node or Python command through its compose tool service
  Then the command runs in a container and finishes
  And no Go, Node or Python install on the host is used

Scenario: Go tests run in the Go container
  Given the stand-ins are not running
  When a developer runs "go test ./..." through the Go tool service
  Then the backend unit tests run in the container and report their result
  And "go test -race ./..." also runs there

Scenario: Go lint and vulnerability checks run in the Go container
  Given the Go tool service
  When a developer runs golangci-lint and govulncheck through it
  Then both run in the container with the versions pinned in backend/go.mod
  And a lint finding or a known vulnerability fails the command
```

## Notes

**Agent brief**

- **Role:** `infra-engineer` (see `.claude/skills/tickets-from-spec/references/roles.md`)
- **Goal:** `docker compose run --rm go <command>` runs `go test ./...`, `go test -race ./...`, `go vet`, golangci-lint, govulncheck and the migrate command in `backend/`.
- **Read first:** [local development guide](../local-development.md), [ADR-0005](../adr/0005-local-cloud-emulation.md), [ADR-0007](../adr/0007-backend-go-and-test-stack.md), the S1-07.01 discovery note, `docs/code-review/eu-only-processing.md`
- **Files to change:**
  - `compose.yaml`, the `go` service under profile `tools`, cache volume, working directory and pinned image
  - `infra/dev/go/Dockerfile`, only if the stock image lacks a needed package (for example a C toolchain for `-race`); otherwise leave it out and say so in the PR
- **Do not touch:** `backend/`, `frontend/`, `scripts/dev/`, `docs/local-development.md` (S1-07.13). The Node, Python and app services (S1-07.07 to S1-07.10). Never read, search, print or create `.env` files.
- **Covers scenarios:** `Each toolchain runs in a container with no host install beyond Docker`; `Go tests run in the Go container`; `Go lint and vulnerability checks run in the Go container`
- **Done when:** the three scenarios pass by reading `compose.yaml`, and a live run through the service passes: `docker compose run --rm go go test ./...`, `go test -race ./...`, `go tool golangci-lint run ./...` and `go tool govulncheck ./...` in `backend/`. The PR shows the run on a host with no Go installed. Image tag and digest are pinned, with the checked date in a comment.
- **Out of scope:** Integration tests against PostgreSQL (they use the same service with `DATABASE_URL` from S1-07.10). Docs (S1-07.13). CI (S1-07.11).
- **Open questions:** None.

Definition of done note: no AI, consent, retention or body data is touched, and no UI is changed, so those two lines do not apply.

Race detector: with the Go container, `go test -race` no longer depends on host cgo. S1-07.12 amends ADR-0007 to say so.
