## User story

```gherkin
Feature: Photos are removed from storage even when storage fails once
  As a considered dresser
  I want my photos deleted from storage after I withdraw consent or delete my account
  So that no photo stays behind after I have asked for it to be removed
```

Context: ADR-0013, erasure paths 1 and 3. S1-06.23 records each photo key in the queue inside the database transaction. This ticket is a background job that deletes each object and removes its key only after the object store accepts the delete.

## Acceptance criteria

```gherkin
Scenario Outline: The object store's answer decides whether a queued key is removed
  Given a queued photo key whose object delete failed earlier
  When the retry job runs and the object store <answer>
  Then the key <outcome> on the queue

  Examples:
    | answer                 | outcome |
    | accepts the delete     | is removed |
    | still rejects the delete | stays |
```

## Notes

**Agent brief**

- **Role:** `backend-engineer` (see `.claude/skills/tickets-from-spec/references/roles.md`)
- **Goal:** a retry job that lists the queue, deletes each object through the existing S3 client behind a port, and removes a key only after the object store accepts the delete. The job logs counts, never keys.
- **Read first:** [ADR-0013](../adr/0013-server-side-outfits.md) (erasure path), [security guide](../security.md) §10 and §14, [backend ruleset](../code-review/backend-ruleset.md), [ADR-0011](../adr/0011-s3-client-library.md) (S3 client).
- **Files to change:**
  - `backend/internal/photodeletion/`, the new domain package: the job, its port and the in-memory fake
  - `backend/cmd/api/`, the wiring of the job
- **Do not touch:** `backend/migrations/`, `backend/internal/db/` (owned by S1-06.23), the object-storage package, the MCP tools.
- **Covers scenarios:** none. The scenario above is this ticket's own.
- **Done when:** `go test ./...` and `golangci-lint run` in `backend/` pass, and the Scenario Outline passes both rows. Logs record the number of retries, never the keys or photo names (security guide §10).
- **Out of scope:** the queue table and the recording (S1-06.23), and the account-deletion call path (S7-01).
- **Open questions:**
  - Which job runner runs the retry? If the backend has none, a new mechanism is a new dependency and needs an ADR before code (CLAUDE.md).
  - Give-up rule. Proposed default: retry with backoff, raise an alert once a key has failed for 24 hours, and never drop a key while it is queued. The DPO confirms the rule before launch.
