## User story

```gherkin
Feature: Signed-in person's outfits are stored on the server
  As a considered dresser
  I want my outfits saved to my account when I am signed in
  So that my AI client can create and read them
```

Context: the store for outfits for signed-in people, as the proposed ADR-0013 describes. The schema, consent rules and erasure path come from that ADR, not from this ticket. Anonymous outfits stay on the device (S1-02).

## Acceptance criteria

```gherkin
Scenario: A person cannot act on another person's items
  Given person A owns an item and person B is signed in
  When person B calls "outfit_create" with A's item ID
  Then the call returns "not found"
  And no outfit is saved
```

## Notes

**Agent brief**

- **Role:** `data-engineer` (see `.claude/skills/tickets-from-spec/references/roles.md`)
- **Goal:** a PostgreSQL table for outfits owned by an account, with a migration and a repository, as ADR-0013 accepts.
- **Read first:** ADR-0013 (accepted 2026-11-02, answers in its open-questions list), [ADR-0008](../adr/0008-postgresql-data-store-and-migrations.md), [backend ruleset](../code-review/backend-ruleset.md) section 4 (SQL rules), [consent and GDPR rules](../code-review/consent-and-gdpr.md).
- **Files to change:**
  - `backend/migrations/000002_wardrobe_owner_key.up.sql` and `.down.sql`, the `(owner_sub, id)` unique key on `wardrobe_items`. Use `CREATE UNIQUE INDEX CONCURRENTLY`, then `ALTER TABLE wardrobe_items ADD CONSTRAINT ... UNIQUE USING INDEX`. Keep it in its own file, because `CONCURRENTLY` cannot run inside a transaction. Check the plan against the migration tooling before it runs (ADR-0013).
  - `backend/migrations/000003_outfits.up.sql` and `.down.sql`, the `outfits` and `outfit_items` tables with the composite foreign keys in ADR-0013
  - `backend/internal/db/outfits.go`, the repository with owner-scoped queries only. It maps a foreign-key violation on a link to "not found"
- **Retention:** outfits are kept while the account exists and the wardrobe-photo consent is granted. They are erased when that consent is withdrawn, when the owner deletes the item (outfits left with no items are deleted in the same transaction), and when the account is deleted. Backups follow the 6-month window in security guide §14, which is provisional until the DPO confirms it.
- **Do not touch:** the wardrobe migration `000001_wardrobe.*.sql` (never change a merged migration), the MCP tools, the on-device store.
- **Covers scenarios:** none. This is the store the outfit tool uses. The scenario is listed here because this ticket enables it.
- **Done when:** `go test ./...` and `go test -tags=integration ./...` pass against the compose stack (ADR-0007), and these tests pass:
  - a link from one owner's outfit to another owner's item is rejected by the database, and the repository returns "not found"
  - withdrawing wardrobe-photo consent deletes the owner's outfits, items and consent change in one transaction
  - deleting one item removes it from every outfit and deletes outfits left with no items
  - deleting the account removes the owner's outfits and items
- **Before real data:** the database resource is provisioned in `fr-par` (ADR-0008, accepted 2026-11-02), and the DPO review is accepted (ADR-0013, 2026-11-02). Check the resource region when it is provisioned.
- **Out of scope:** the MCP tool (S1-06.14). S3 photo deletion after withdrawal and account deletion is S1-06.23.
- **Open questions:** None. The answers and the DPO acceptance are in ADR-0013.
